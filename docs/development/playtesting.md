Use `npm run build` followed by `npm run preview` for a frozen local playtest. Record the page’s build identifier and follow the versioned [assessment protocols](../../assessments/protocol/F1.md). Automated and AI reviews are not human acceptance.

For an interaction report, use **Record an issue** in the left sidebar, then Start recording, reproduce, Stop recording and Save recording. The local JSON records build, checkpoint, timed actions and command results. It is a diagnostic timeline, not qualification replay. Nothing is uploaded by this local recorder.

## Remote setup

<!-- doc-review {"version":1,"fingerprint":"147a75ca73d6ef355cd323b32d8664f48c533ca8e93432b26fc6bd5343cb0dc0","dependencies":"docs/development/.reviews/playtesting/remote-setup.json","dependencyDigest":"d6a9f4b9d42fd48bd454696589394b064d07bd4d77f906413bf93980e9f3d1ee","disposition":"updated","rationale":"Documented atomic Node session publication, sync retry with retained v2 identity, restart cleanup of unpublished directories and preservation of legacy incomplete metadata. Remote playtests can use `node scripts/playtest-server.mjs` with `PLAYTEST_PUBLIC_DIR` pointing at a frozen build, a separate private `PLAYTEST_DATA_DIR`, and a random `PLAYTEST_TOKEN` of at least 32 characters. The server binds loopback port 4180; expose it through an HTTPS tunnel and share `/join?token=...`. The invitation grants access to the workshop, not stored sessions. The player explicitly starts tab capture and can send text or microphone feedback tied to a view/state anchor. Pending uploads persist in the separate v2 IndexedDB outbox and retry with identity-checked receipts; keep the tab open until all are received. Tab capture requires a desktop browser supporting screen sharing; choose the workshop tab. Microphone use is optional. Server limits are 2 MB/event, 10 MB/media chunk and 1 GB/session; the browser stops capture if its offline queue reaches 100 MB. To review received evidence locally, run `node scripts/export-playtest.mjs <private-session-directory>` and open the resulting `review.html`. Remote usability recordings do not replace qualification evidence.

Node session creation publishes a flushed temporary directory atomically. A failed parent-directory sync keeps the v2 request identity for exact retry. Restart removes unpublished creation directories and preserves older incomplete metadata-only directories under private `.incomplete-*` names; a corrupt recording journal still fails closed. Rejoin after restarting the Node server.

Remote playtests show a receipt beside each submitted comment after the server acknowledges it. Finishing stops capture and waits for the final recording uploads before confirming that the session is saved and the tab can be closed.

The remote feedback bar stays the same size while recording. Video and action uploads run automatically; routine queue counts are hidden. Upload problems remain visible, and Finish session confirms success only after all recording data is received.

The [server](../../scripts/playtest-server.mjs#implementation), [browser client](../../src/application/remote-playtest.mjs#implementation) and [exporter](../../scripts/export-playtest.mjs#implementation) own admission, upload and review behavior. Keep the data directory outside the served public directory. Do not commit invitation tokens or recordings.

These implementation links cover admission, capture and export code plus declared dependencies. They do not assert the contents of a served workshop build or a player’s uploaded recording; identify those separately for each playtest.

An unmounted capture view stops recording and input immediately. An upload already dispatched retains its existing bounded timeout and may acknowledge its durable outbox entry. Disposal starts no further uploads; a future mount recovers unsent entries.

## Cloudflare hosting

The Cloudflare adapter serves the workshop and a private v2 capture API from one origin. Production uses `https://simulacrum.build`. Staging and production require separate Cloudflare accounts, credentials, R2 buckets and Durable Object namespaces. The invitation enables uploads to known sessions within its generation; it does not grant recording reads. A separate admin bearer controls export and deletion. Cookies are signed, host-only, Secure and expire after seven days. Rotate the invitation generation to revoke cookies. Preserve the signing secret across code deployments.

[The Worker](../../scripts/playtest/worker.mjs#implementation) owns HTTP authentication, exact-origin admission and static-asset access. [The capture store](../../scripts/playtest/cloud-store.mjs#implementation) owns SQLite session/receipt metadata and private R2 payloads. The fixed `capture-v2` object name persists across versions. Protocol v2 acknowledges an upload only after its immutable R2 object and durable receipt exist. Retries with different bytes conflict. Deletion overwrites all reserved keys with permanent zero-byte markers before releasing payload capacity; never configure a lifecycle that deletes those markers. Cleanup retries through alarms and independent five-minute reconciliation. Provider outage leaves deletion pending and charged. Live deletion does not promise removal from provider backups or downloaded exports.

Limits are 20 retained sessions, 1 GiB per session, 20 GiB aggregate payload accounting and an 8 GiB lifetime metadata ledger. Cloud accounting includes 4 KiB per upload pointer. Human sessions expire after 30 days. Synthetic runs reserve payload, session slots and lifetime metadata before publication, expire after two hours and clean up only their own recordings. Repeated verification does not clear human sessions. Body readers admit at most two uploads, enforce byte limits and idle/total deadlines, and reject overload rather than buffering a queue. The retained Node adapter uses the same pre-read admission bound while retaining its filesystem accounting. Storage response deadlines retain the occupied admission slot until the underlying operation settles; new writes fail closed during an unresolved storage timeout.

The [v2 outbox](../../src/application/capture-outbox.mjs#implementation) uses its own IndexedDB database. Payload removal and an identity-checked acknowledgment commit together. Other tabs reconcile durable receipt state, so closing the uploading tab does not lose acknowledgment evidence. Terminal failures preserve bytes and suspend every queued upload for that session. Other sessions continue. The saved-recording picker targets retry, local discard and server-deletion requests without requiring a session ID. Local payloads are bounded to 100 MiB and metadata to 16 MiB. Browser permissions are always explicit; tab selection is the browser picker's choice, not proof that the user chose this workshop.

Run `npm run build`, then `npm run playtest:local` for local Workers development. Put synthetic `INVITATION_TOKEN`, `COOKIE_SECRET` and `ADMIN_TOKEN` values of at least 32 characters in an ignored `.dev.vars` file. The checked Wrangler configuration is local-only; it contains no real account IDs or production bindings. Do not invoke an unconfigured remote deployment. Local Workers testing uses emulated SQLite/R2. `verify-cloud-playtest` and `verify-remote-playtest` execute the same real-browser recording flow against cloud and Node adapters; `verify-cloud-runtime` exercises workerd without media permissions.

For hosted evidence, set `PLAYTEST_ADMIN_TOKEN` in the process environment and run `npm run playtest:download -- <https-origin> <session-id> <new-private-directory>`. The [downloader](../../scripts/playtest/download.mjs#implementation) reads a fixed journal cutoff, checks every payload hash and creates the existing local review layout. Exact event bytes are retained as `event-<sequence>.json` with their byte count and hash in the derived journal. Then run `node scripts/export-playtest.mjs <private-session-directory>`. Missing/corrupt bytes fail the export. A session-end event does not prove continuous recording or delivery of every final callback; the review says completion is not proven.

## Release operations
<!-- doc-review {"version":1,"fingerprint":"d3d10012b1f9e810ae488af5c842cc4d63562fc93761a4d127471bbcb141b018","dependencies":"docs/development/.reviews/playtesting/release-operations.json","dependencyDigest":"b3744fada4d5e10a4687dbfc0b903bcdc6380f184943fe6ec92494fd9cbe26aa","disposition":"updated","rationale":"Documented full pre-publication staging capacity held across both phases, emergency code restoration before application-admin calls under existing owner/provider checks, and the enforced five-minute median-growth predicate with complete browser samples. [Release policy](../../scripts/playtest/release-policy.json) names the initial `v2` release branch. The [shared release tool](../../scripts/playtest/release.mjs#implementation) freezes selected working-tree inputs, runs release verification in an isolated private copy and builds one package. `npm run release:prepare -- .release-private/<new-name>` accepts modified/untracked source without committing it. It rejects input drift and keeps the source copy outside public artifacts. The package manifest binds the actual Worker/assets bytes, source digest and capture protocol. Expired or altered packages cannot be promoted normally.

The [GitHub release workflow](../../.github/workflows/ci.yml) runs staging only after same-commit automated/browser checks on the release branch. Production uses the separate [manual dispatch](../../.github/workflows/deploy-production.yml), selecting a successful release run ID and exact artifact digest and expected production predecessor version at dispatch. Both preflight and atomic admission reject a changed predecessor, including a newer local publication. The dispatcher validates repository, workflow, branch, source and staging evidence; a push or staging success alone never updates production. Configure GitHub staging/production environment deployment-branch restrictions for the trusted release branch before enabling either publisher. Queued staging jobs recheck workflow run order before mutation; an older run cannot replace a newer successful release. Publication also requires enough remaining synthetic reservation lifetime for verification and cleanup. The production dispatch file must be present on the repository's default branch to be selectable; check that setup explicitly without renaming branches.

Each environment needs an independently provisioned release-control Worker with the [publisher coordinator](../../scripts/playtest/release-control.mjs#implementation). Every supported publisher acquires its durable owner record before mutating that environment. Competing publishers fail without changing it. Ownership never expires automatically. Local commands additionally pause and later restore the matching GitHub deployment variable. On a lost response, crash, failed verification or cleanup outage, ownership remains held: stop the old publisher, establish that its remote operations settled and revoke its token if it could resume, then reconcile the actual deployed version before manually completing recovery. Never unlock on elapsed time alone. Ordinary workshop releases must not redeploy or reset the coordinator.

Before enabling automation, provision distinct accounts and private buckets, fixed Durable Object bindings, coordinator credentials, domain/TLS and explicit observability settings. Keep Worker invocation logging, traces, Tail consumers and request-log exports disabled. The [deployment verifier](../../scripts/playtest/verify-deployment.mjs#implementation) fails closed when effective settings or account-isolation checks cannot be read or verified. Real account configuration and browser canary checks require authorized staging access; local tests do not establish them.

Configure `STAGING_RELEASE_CONFIG` and `PRODUCTION_RELEASE_CONFIG` as nonsecret JSON repository variables with the environment's account ID, other account ID, Worker name, exact origin, coordinator URL, expected initial predecessor and reviewed `wrangler` configuration. Both configurations also require `captureNamespaceId` and an `isolationTargets` inventory: `authorization: "disposable-probes-only"` and `currentWorker`, `otherWorker`, `currentBucket`, `otherBucket`, each naming an independently provisioned, empty `simulacrum-isolation-*` probe in the corresponding account. Keep probe resources separate from capture resources. The verifier checks current-account Worker read/write and bucket read, plus explicit denial of other-account Worker read/write and bucket read/CORS write. Probe secrets are synthetic and removed after a permitted write; the probe bucket has an empty CORS policy. Repeat the matrix with each environment credential. These bounded capability tests supplement reviewed account scoping. Effective capture bindings must match the pinned R2 bucket, namespace and class before and after publication; the [five-minute Cron](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/schedules/methods/get/) must also be present. Production also needs its zone ID. Set `DEPLOY_STAGING_ENABLED` and `DEPLOY_PRODUCTION_ENABLED` to literal `true` only after bootstrap checks pass. Repository secret `RELEASE_READ_TOKEN` supplies a repository-scoped GitHub App or fine-grained token with Actions read and [Variables read](https://docs.github.com/en/rest/actions/variables#get-a-repository-variable) for live pause/provenance checks (the built-in workflow token is still used for artifact downloads). Repository secrets `STAGING_CONTROL_TOKEN` and `PRODUCTION_CONTROL_TOKEN` authorize the preflight coordinators; they do not contain Cloudflare deployment authority. Each matching GitHub environment supplies its own account-scoped `CLOUDFLARE_API_TOKEN` and `PLAYTEST_ADMIN_TOKEN`. The production token must be able to inspect required zone logging settings; missing read permissions block publication rather than bypassing checks.

For a local deployment, `npm run release:deploy -- <private-release-directory> <private-config.json>` selects the exact package. Its configuration names `environment`, `accountId`, `otherAccountId`, `workerName`, `origin`, `coordinator`, `repository`, `expectedPredecessor`, `artifact`, `wranglerConfig` and, for production, the successful staging evidence file. Supply environment-specific Cloudflare/admin/control tokens and a GitHub token authorized to manage the pause variable. The tool preserves storage and runs post-deployment verification plus run-owned synthetic cleanup before releasing ownership. A failed deployment may already have changed code; it must be recovered explicitly, not retried with a new owner.

Keep the last successful v2-compatible package privately for rollback. Rollback must retain v2 routes, receipt semantics and create-only payload writes, use the same publisher exclusion, and preserve R2/SQLite, signing secrets, coordinator and custom domain. Never deploy a legacy-only backend over v2 sessions or perform destructive migrations during a code rollback. Set `CAPTURE_NEW_SESSIONS=false` to stop new sessions while existing uploads drain.

Before normal staging publication, reserve all 20 session slots, 20 GiB of payload accounting and 1 GiB of lifetime metadata for the entire experiment. The metadata allowance covers the maximum preliminary capture record count and its replayed event rate. An abandoned reservation blocks before publication. Preliminary cleanup fences its payloads and atomically returns slots/bytes to the same reservation; it never releases those slots to competing sessions. Spent lifetime metadata stays charged. The twenty-client load reuses that reservation, then releases it after cleanup.

Staging publication runs a real 30-minute browser capture followed by a bounded 20-client upload experiment using the full captured media sample distribution and measured event traffic, shaped to a 5 Mbps client uplink and approximately 100 ms RTT. Throttled or timed-out events retain the exact request through retry. The report includes retry/timeout counts, producer backlog, real browser outbox samples, export time, stored bytes and a separate pair of concurrent 10 MiB uploads. CPU and RSS measurements explicitly describe the load-generator process; they are not Worker resource measurements. The load gate requires complete thirty-minute browser samples and final drain. It rejects five consecutive one-minute queue medians when every adjacent increase exceeds 128 KiB and the total increase exceeds 1 MiB; short bursts that drain are permitted. Missing or sparse evidence fails. The load result must meet the latency/backlog targets before staging becomes eligible. The two-reader configuration is a measured constraint, not a promise of 20 simultaneous recordings. A failing load check keeps publication incomplete and ownership held for recovery; it does not silently increase memory admission.

Use `node scripts/playtest/release.mjs rollback <previous-package> <private-config.json>` for an explicitly selected, previously verified production package. The production dispatch also has an explicit compatible-rollback mode taking a previous successful production run. For an interrupted local publisher, after stopping it and establishing remote quiescence, use `node scripts/playtest/release.mjs recover <selected-fresh-package> <private-config.json> <private-owner-file> --publisher-stopped`. Supply the actually deployed predecessor and the original owner record. This supports first-staging recovery without any previous production package, reuses an existing owner file, and can restore code while the currently deployed capture admin API is broken. Explicit recovery and compatible rollback keep package, coordinator, predecessor and provider binding checks, restore code first, then clean any known abandoned reservation and acquire verification capacity. They retain ownership if subsequent verification or cleanup fails; restoration alone is not a successful release. For a previously verified production rollback package use `recover-rollback` instead. All normal exceptions after reservation trigger run-owned cleanup; temporary raw exports, screenshots and capture diagnostics are purged on success and failure. A process kill or lost reservation response is recovered through the retained owner record or the two-hour synthetic expiry and Cron; local private remnants from a killed process must be removed during operator recovery. This reuses ownership; the flag is an operator attestation, not automatic proof that a remote operation stopped. Do not use it while the old process or credential can still mutate production.
